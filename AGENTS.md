# Agent instructions

- This repository is public. Keep it generic: don't reference private deployments, servers or modules built on top of it.
- Stick to best practices of the frameworks used; check current documentation instead of relying on memory.
- Before pinning a new dependency, check its current version on the registry (`npm view <pkg> version`). Pin exact versions.
- Write concise comments that explain current behavior, constraints or intent. Don't document refactor history.
- Tables holding per-guild data are created with `guildTable()`; tables shared by all guilds with `globalTable()`. Never create tables any other way: the startup checks reject any table that doesn't keep guilds apart (RLS, a policy, a cascading foreign key to `core.guilds`).
- Startup schema work goes through `prepareDatabase()`: it creates the app role if needed, migrates core and the modules, creates the module roles, grants core to the app role and each module schema to its module role, revokes the app role on unloaded modules' schemas, and checks guild isolation under one advisory lock. Don't call the migration, role, grant or check steps separately at startup. A module's role can write its own module's global tables; core's global tables are read-only for handlers.
- Each module's database work runs as its own role (`moduleRoleName(appRole, module)`), set per transaction by `ScopedDb.run()`. The plain app role has no access to module schemas; pass the module's role (`ModuleRuntime.dbRole`) whenever core code builds a `ScopedDb` for a module.
- Database access in handlers goes through `ScopedDb.run()`; one `run` is one transaction.
- Modules are `defineModule()` definitions. They declare listeners (`on(...)`) and hooks; they never call `client.on` themselves.
- Handlers `await` all database work inside the handler. A Drizzle query awaited outside the handler's scope loses the guild and the acting user.
- A module emits only its own events and uses other modules only through their `api` (declared in `dependsOn`); a module with a `db` has a role that can't reach other modules' or core's tables (a module without one runs as the app role; it shouldn't touch core's tables either). The roles guard against mistakes, not hostile module code: never run `set role` or `reset role` in a module.
- Tests never connect to Discord. Use `createNativeTestClient` with `FakeDiscordHttp` for native Discord.js operations; `FakeClient` and fake interactions from `@bronto/core/testing` remain available for core behavior.
- Interaction handlers answer only through `ctx.reply`/`ctx.followUp`/`ctx.defer`/`ctx.showModal` (components also `ctx.update`/`ctx.deferUpdate`), and throw `UserError` for messages meant for the user.
- Module schema files import `guildTable`/`globalTable` from `@bronto/core/tables`; prefer this over `@bronto/core`, since drizzle-kit loads schema files and the main entry pulls in discord.js, pino and the runtime.
- Never keep a transaction (`ctx.db.run`) open across a Discord API call.
- Check gates and asks (`ctx.check`, `ctx.ask`) outside `ctx.db.run`; listeners answer in dependency order, the first denial wins, and errors, invalid answers and the 5 s timeout count as denials; collectors skip failing listeners instead of denying.
- A queued task (`ctx.queue.run`) never waits for a task of its own key.
- Modules with timers or in-memory state per server stop them in `hooks.guildStopped` and rebuild them in `hooks.guildReady` (which may run more than once).
- Docs come in three tiers. `docs/user/` (and `modules/<name>/docs/user/`) holds the pages `/help` shows in Discord and follows `docs/api/writing-user-docs.md`; a module sets `docs` and calls `checkDocs` in its tests. `docs/admin/` holds self-hosting docs and `docs/api/` the developer docs, both ordinary GitHub Markdown. Module READMEs only summarize and link to the tiers.
